# 标准软件 UI 与设计规范

目标是让多个页面共享同一套可维护的视觉与交互语言，并能由设计稿和代码共同验证。

## 先理解产品

确认用户角色、核心任务、信息架构、权限、设备尺寸与已有产品约束。已有界面或组件库先盘点并提炼实际使用的规则；新项目则从一个代表性任务和页面建立最小规范，随后扩展。不要照搬成熟系统的全部组件数量或把参考库的默认配色当品牌规范。

## 建立规范

1. 定义基础与语义变量：品牌/中性色、文本/背景/边框/反馈色、字号与行高、间距、圆角、阴影、栅格和断点。说明明暗主题的映射、对比度及数字/表格字体需求。变量命名能表达用途，避免页面里散落硬编码。
2. 按实际流程设计核心组件及变体：尺寸、层级、默认/悬停/聚焦/按下/禁用/加载/错误/成功等状态。优先按钮、输入、选择、表格、导航、反馈、弹层；图标和图表建立风格规则与语义映射。
3. 以列表、详情、表单、工作台等代表性模板验证组件组合。写清筛选、分页、排序、保存、取消、撤销、批量操作、权限不足、空状态、加载和失败恢复的行为。
4. 若使用 Figma，建立变量/样式、Auto Layout、组件和变体，并将页面实例真正绑定到规范。若直接做代码，建立对应 token 与组件接口；两者同时存在时检查命名和值的映射。避免只画一页展示图却声称组件库已完成。

## 设计与验证

用真实长度的标题、数字和表格内容检查密度、换行、截断和响应式。通过键盘导航、可见焦点、控件尺寸、对比度与错误提示检查可用性。至少走通一条任务链，从入口、输入、校验到结果或失败恢复；检查未登录与角色切换后是否泄露上一用户信息。

交付可查的 token/组件说明、页面模板、状态规则及与开发的映射。组件清单按项目取舍，参考 [references/component-states.md](references/component-states.md)。如果只做审查，报告已存在规则、缺口和可复用的修正建议。
